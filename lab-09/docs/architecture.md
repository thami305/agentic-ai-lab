# Lab 9 — Architecture

## What this lab is

A regression harness for the lab-02 agent and the lab-03 graph. Fifty
versioned golden cases pin the behavior both systems exhibit today; a merge
gate re-runs them and refuses green unless every threshold in
`eval/thresholds.json` holds. The lab's teaching model — *the model proposes,
deterministic code decides* — is applied to the lab itself: deterministic
checks (schema, citation validation, terminal, tool allow-list) run first and
decide; the "model grader" is an explicitly limited stub that only tracks
surface properties.

## Components

**Golden set (`data/golden.jsonl`, generated by `scripts/gen_golden.py`).**
One JSON object per line: `{id, version, category, target, input,
expectations}`. `target` is `"agent"` (lab-02 `Agent` with a named stub
backend) or `"graph"` (lab-03 `build_graph` with a named policy).
Expectations pin `terminal` (`publish` | `clarify` | `review` | `declined` |
`error` | `stop`), `allowed_tools`, `min_claims` for publish cases, and
`forbidden_text` / `forbidden_in_reasoning` where relevant.

The generator is record-and-pin with a hand-review step: each spec declares
the *intended* terminal, the script runs the case and asserts the observed
terminal matches before writing. Two specs surprised the author during
generation and were investigated, not blindly pinned:

- `h12` (graph, "When does finance expect the second site to break even?")
  routes to `review`, not `publish`: the lab-03 packet's revised finance note
  (DOC-FIN-5) conflicts with DOC-FIN-2 and the conflict detector fires.
  Replaced with a clean finance question.
- `a07` (graph, "Which location should the second warehouse be built in?")
  also routes to `review` — the retrieved passages include the conflicting
  finance pair. Kept as `review`: an ambiguous question surfacing
  conflicting evidence *should* go to human review.

**Tracer (`src/lab09/tracer.py`).** Instruments without modifying lab-02 /
lab-03 source: a delegating proxy wraps `backend.next()` (model spans),
registry rebuild wraps each tool `fn` (tool spans; raised exceptions also
emit error spans), graph node `fn`s are wrapped in place on the per-run
`Graph` object (path spans), and the lab-09-owned policy instance gets
wrapped `retrieve`/`synthesize` (tool spans; failed retrieve attempts emit
retry spans). One JSON trace per case: `{case_id, spans, path}`. The graph
runtime already records `state.path`; the tracer copies it.

**Runner (`src/lab09/runner.py`).** Executes cases and applies the
deterministic checks, in order: expected terminal reached; schema (a shipped
brief exists exactly when terminal is `publish`); citations (every *shipped*
brief passes the real `lab02.validate.validate_brief`, counted per claim);
tool names ⊆ `allowed_tools`; `min_claims`; forbidden-text checks. A bad
brief routed to `review`/`clarify`/`stop` was correctly *rejected*, not
shipped — it contributes 0 unsupported claims. The gate metric
`max_unsupported_claims` therefore measures what would have reached a user.

**StubGrader (`src/lab09/grader.py`).** Grades on surface properties only:
terminal match, claim count, tool allow-list, forbidden-text absence, brief
parses as `ResearchBrief`. It deliberately does *not* re-check citations —
that is the deterministic layer's job.

**Gate (`src/lab09/gate.py`, wrapper `eval/gate.py`).** Loads thresholds from
`eval/thresholds.json` at runtime (never hardcoded), runs all 50 cases plus
the 10-entry calibration subset, and reports red/green per threshold:
`min_pass_rate` 1.0, `max_unsupported_claims` 0, `min_agreement` 0.9.
Exit code 0 = green, 1 = red.

## Honest caveats

**The stub grader is not a judge.** Its documented limits (see the
`grader.py` docstring): it cannot assess factual correctness of a claim
against its quoted passage (only string presence), completeness, whether a
decline was warranted, or injection semantics beyond string matching. A
claim "revenue doubled" quoting a passage about warehouse utilization passes
the stub grader. Calibration agreement of 1.0 means the grader *tracks the
deterministic checks* on the labeled set — not that it judges quality. Do
not promote it to a real LLM judge without re-reading those limits.

**Record-and-pin expectations can fossilize bugs.** `min_claims` and
`allowed_tools` are derived from observed runs. If the pinned behavior was
wrong, the gate defends the wrong thing. Mitigations in place: the
generator asserts intended terminals, the golden file was hand-reviewed, and
the centerpiece regression test proves the gate actually bites (see below).
Still, any behavior change needs a human to re-approve the regenerated file.

**Coverage is behavioral, not exhaustive.** 50 cases cover the known failure
modes from labs 1–3, but a novel model failure (e.g. a subtly mis-quoted
passage that still validates) would only be caught if a case pins that
exact shape. The golden set should grow with every real incident.

**The regression test patches one seam.** Monkeypatching
`lab02.agent.validate_brief` disables the citation post-validator on the
*agent* path only (lab-03's `nodes.py` binds the real validator at import).
That is sufficient for the centerpiece test — four fabricated-citation cases
flip from `error` to `publish` and the gate goes red — but a regression in
the *graph* validator would need its own test.
